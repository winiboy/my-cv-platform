THE REGRESSION THIS STORY INTRODUCED AND FIXED
- An edit made within the 500ms debounce window was dropped SILENTLY. The
  persist effect's cleanup did clearTimeout, so the write was never ATTEMPTED
  and neither error path ran. Because the account now holds a full 19-key model
  that outranks the cache, the user would have watched their most recent change
  revert with no diagnostic anywhere. Before this story that edit lived in
  localStorage and survived, so it was a regression - and the PRD's accepted
  cost covers a FAILED persist, not an UNATTEMPTED one.
- Found by code-reviewer pass 1, not by the implementation or by any suite.
- Fix: the debounce state machine moved to src/lib/layout-persistence.ts. The
  persist effect no longer has a cleanup at all - superseding a pending write
  is submit's job - and a second effect flushes on unmount, pagehide and
  visibilitychange. flush() is idempotent.
- sendBeacon was rejected with a verified reason: POST only, no custom headers,
  so it can carry neither the Authorization bearer nor the apikey PostgREST
  requires. A keepalive fetch via a second Supabase client was also ruled out -
  createBrowserClient returns a browser-wide singleton, so a second caller's
  options are ignored or applied globally. Both claims verified against
  node_modules by the implementer and re-verified by the reviewer.
- A case neither the brief nor the review anticipated: a naive flush
  resurrects undone edits. Drag to B, drag back to A inside the window,
  navigate - a replayed B would write a value the user had cancelled. submit
  clears pending before it decides, so that case writes nothing. Tested.
