WHAT THIS STORY ACTUALLY FOUND

The named defect was a parameter-name mismatch: middleware wrote ?redirect,
the login form read ?callbackUrl, so every deep link was discarded. Fixed by
aligning on callbackUrl - the name with five live producers and the only
reader - rather than reading both, which would have created two spellings for
one concept. The deep link's own query string now travels with it.

But the story also exposed a LIVE OPEN REDIRECT in shipped code. Because
?callbackUrl was already read via the marketing tools links, an attacker could
send /en/login?callbackUrl=/\evil.test and land a signed-in user off-origin
from a legitimate login flow. Five inputs defeated the old validator:
/\evil.test, /\evil.test, and raw TAB, LF and CR variants. All confirmed by
execution, not inspection.

AND THE FIRST FIX INTRODUCED A DIFFERENT ONE

Round 1 tightened the validator and shipped a NEW open redirect on a class the
old code handled safely. getSafeRedirectUrl validated the parsed URL object -
correctly same-origin - then returned resolved.pathname, which for /.//evil.test
is the string "//evil.test". Six dot-segment inputs escaped. code-reviewer
navigated a real browser off-origin to prove it (chrome-error://chromewebdata/,
page title evil.test) and traced Next 14.2.33's useNavigate -> isExternalURL ->
handleExternalUrl -> location.assign.

Fixed by extracting isSingleSlashRelativePath() and applying it to BOTH the
candidate and the reconstruction, immediately before returning.

Final differential, verified independently: old validator 5 escapes, new
validator 0 across 22 hostile inputs in 4 classes, 9/9 legitimate destinations
preserved.

THE LESSON, WORTH CARRYING

Validate the representation you RETURN, not the one you inspected. The origin
check was not lying - `resolved` genuinely was same-origin. The danger was
created afterwards, by serializing it back to a string that could begin with //.

Two related process notes:
- My own differential declared the round-1 validator clean. It was not. I chose
  probes matching the bug I already knew about, so dot-segments were absent. A
  clean differential over the wrong probe set is indistinguishable from a clean
  differential.
- code-reviewer found a THIRD representation neither of us had considered:
  Next's addBasePath -> normalizePathTrailingSlash rewrites the approved string
  after validation. It ported those helpers and re-fuzzed through the real
  chain - 13,139 inputs, 243 strings altered downstream, 0 that became unsafe,
  because the transform only strips a trailing slash and cannot manufacture a
  leading //. If basePath or trailingSlash is ever configured, that chain needs
  a fresh look.
- It also caught a stale-build hazard: its own round-1 server still held the
  port and would have served the vulnerable bundle. It verified the served
  bundle text directly rather than trusting the build.

Exhaustive re-hunt for a further class: 67,412 generated inputs over a hostile
alphabet, including Unicode solidus lookalikes, encoded traversals, query and
fragment smuggling and @-userinfo forms. Zero escapes, zero legitimate
destinations broken.

Carried forward, not blocking:

  This change routes more traffic through that branch, so it matters more now.
