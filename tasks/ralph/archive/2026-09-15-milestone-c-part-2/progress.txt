THE DESIGN
A shared hook over a pure rules module, the same split Part 1 used for
layout-persistence.ts. src/lib/resume-layout-store.ts holds the decisions with
no React; use-resume-layout.ts holds one useState<ResumeLayoutModel> plus the
lifecycle glue. Both surfaces unpack it into locals with the names their render
bodies already used, so NO template, control or prop signature changed.
Not a context: the two surfaces are separate routes and never co-exist in one
tree, so a provider spans nothing. They need one definition, not one instance.
Not nineteen useStates: everything downstream already wanted the whole model,
and both files previously reassembled it with a nineteen-entry useMemo
dependency list - a standing invitation to omit a property.
Storage is passed as a THUNK, because window.localStorage can throw on property
access and both surfaces already had that access inside their try.

THE FALSE INVARIANT THE FIRST REVIEW CAUGHT
The comment justifying the type aliasing claimed that adding an id to
VALID_SIDEBAR_IDS would become a compile error. It would not. The reviewer did
not argue - it replicated the pattern with 'awards' added, ran the repo's own
tsc --strict, and got EXIT 0. The new id flowed through the unchecked
`as SidebarSectionId[]` cast, fell through every `if (sectionId === ...)`, and
rendered nothing: precisely the silent-drop bug the comment claimed was
prevented. Aliasing catches removal/rename; it does not catch addition, because
DocxGeneratorSettings.sidebarOrder is string[] and the dispatch was a
non-exhaustive if-chain.
Critical rather than cosmetic for two reasons: it was the entire argued
justification for AC-2's type change, and F-5 establishes docx-modern.ts
carries the identical pattern - so a false invariant was about to be copied
into a second generator.
Fixed by making the claim TRUE rather than by softening it: both section
dispatches are now exhaustive switches closing on

E-1 THE INTERMITTENT EXPORT STALL - AN ENVIRONMENT CAUSE, NOT A PRODUCT DEFECT
Symptom: a DOCX export request occasionally fails - a 15 s client timeout, or
the server closing the socket at about 10 s - and 2 of 6 full parity runs across
the reviews hit it. A stalled run fails loudly as a collect failure and never
produces a false verdict.

Cause: under the parity flow's concurrent HTTP load, Windows holds a Node
process's socket write or close for about 10 s, freezing that process's event
loop. The deciding control is a standalone probe with no project code, writing
97 bytes every 250 ms over a kept-alive loopback socket, run as HTTP and as raw
bytes in separate processes over the same window: HTTP blocked 14 of 770 writes
(worst 9,957 ms); raw blocked 0 of 1,293 (worst 2 ms). Each component alone was
clean - 400 sequential exports (p99 103 ms), 2,198 Chromium iterations, 947
Supabase samples. During freezes CPU sat at 2 % with 40 GB free and no paging,
and typeperf never paused. The CPU profile places the holds in undici's
header write and socket close.

Refuted with evidence: undici's 10 s connect timeout (connects took 0-1 ms),
localhost resolving to ::1 (every URL is 127.0.0.1), Docker/Kong (GoTrue
answered what arrived in 25-40 ms, and a loopback server with no Docker froze at
the same instants), Sentry egress (egress blocked, still froze), port exhaustion
(under 100 sockets in TIME_WAIT).

Most likely source: AVG Antivirus HTTP inspection. Windows Security Center
lists AVG active as antivirus and as the registered firewall, the Winsock
catalogue holds only Microsoft providers, and HTTP is held while raw bytes are
not. UNCONFIRMED: confirming it means an AVG exclusion for node.exe, or turning
off its HTTP scanning, then five parity runs expecting zero stalls - a
security-software change only the owner can make. Plausibly the same cause as
the open e2e/auth.spec.ts:27 intermittent recorded under US-007 (a 30 s wait is
three 10 s holds).

The rule, recorded in playwright.parity.config.ts as well: this must NOT be
absorbed with timeouts, retries or reduced load. Round 3 added a 60 s
per-request timeout on a cold-start diagnosis that the reviewer's run
contradicted; it was removed. Re-run a stalled run instead.

Orchestrator correction: mid-investigation I told the owner the evidence pointed
to Kong in Docker on WSL2 with DNS retries. The Docker-free loopback control
refutes that; I read a symptom as the cause.
